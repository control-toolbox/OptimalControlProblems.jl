JuMP schemes ​

This page is for users and developers who want to know exactly which nonlinear program (NLP) a JuMP model of this package is, and how the model stores what is needed to read the state, the control and the costate back. It is not needed to use the package.

The OptimalControl modelings return the continuous problem; the discretization is chosen in solve and done by CTDirect. The JuMP modeling has no such layer: each JuMP model is an NLP. To compare JuMP and OptimalControl fairly, the JuMP models reproduce the NLP that CTDirect builds, scheme by scheme.

Exa and the number of controls

Under the :exa modeler of OptimalControl, the controls are declared at the   nodes for every scheme. For :euler, :midpoint and :euler_implicit the Exa NLP therefore has more unknowns than CTDirect's, used only by their bounds and by one extreme path constraint. See #284.

Order of the unknowns and of the constraints ​

The order of the unknowns and of the constraints changes the sparsity pattern seen by the linear solver. It is chosen when the model is built, with ordering:

  • :interleaved (default), CTDirect's order:

    • unknowns: node by node, the state then the control while there is one, (trapezoidal rule) or (one control per step), then ;

    • constraints: for each step   , the dynamics of the step then the path constraints at node ; then the path constraints at node ; then the boundary conditions.

  • :blocks, the same pieces grouped by kind:

    • unknowns: , then all the controls, then ;

    • constraints: all the dynamics, then the path constraints at the nodes , then the boundary conditions.

julia
model = beam(JuMPBackend(); grid_size=100, ordering=:blocks)
model[:ordering]    # :blocks

The NLP is the same in both orders, up to a permutation of the unknowns and of the constraints. The unknowns keep their names (x₁[3]), and model[:constraints] lists the constraints in CTDirect's order for both orderings, so the permutation can be computed from the model.

MOI groups the constraints by type

JuMP passes the constraints to the solver grouped by type: function (affine, quadratic, nonlinear) and set (equality, interval). The order of creation is kept only within a type. The dynamics, path constraints and boundary conditions of a problem are often of different types, so :blocks mostly changes the order of the unknowns.

In the code ​

A problem file declares data ​

A file of ext/JuMPModels/ fills a ProblemData and hands it to the scheme; it writes no discretization itself:

julia
data = ProblemData(;
    state=[Component("x₁"; lower=x₁_l, upper=x₁_u), Component("x₂")],
    control=[Component("u")],
    costate=["∂x₁", "∂x₂"],
    times=v -> (t0, tf),
    dynamics=(x, u, v, t) -> [x[2], u[1]],
    lagrange=(x, u, v, t) -> u[1]^2,
    boundary=[(x₁_t0, (x0, xf, v) -> x0[1], x₁_t0), (x₁_tf, (x0, xf, v) -> xf[1], x₁_tf)],
)
return build(data, grid_size, scheme, ordering, args...; init=init, kwargs...)

The accessors read these keys:

julia
model = beam(JuMPBackend(); grid_size=100)
JuMP.set_optimizer(model, Ipopt.Optimizer)
JuMP.optimize!(model)

T = time_grid(model)          # t_0, …, t_N
x = state(model)              # function of t, interpolating X_0, …, X_N
u = control(model)            # function of t: linear (trapeze) or piecewise constant
p = costate(model)            # function of t, from the duals of the dynamics constraints
objective(model), iterations(model)

The costate is read from the duals of the dynamics constraints of each component, one per step: its sign and time conventions are not yet aligned with OptimalControl (see #326). When the problem also exists in OptimalControl, solution(model, pb) builds a full CTModels.Solution from these values, which can be plotted like an OptimalControl solution.
